# Provider delivery: three ways to obtain a provider

Status: **design, not implemented.** Today a provider exists only where the
repository's example scripts built it (CI or a developer machine), and cargo-libc
needs `--provider FILE` pointing at its descriptor. This document defines how users
will obtain the provider for any release, 2.17 through 2.44, in three ways. All
three produce the **same provider layout** and must pass the **same qualification**.
The [roadmap](ROADMAP.md#provider-delivery) tracks the work.

## What a provider contains

| Part | Origin | Size (all releases, deduplicated, xz) |
| --- | --- | --- |
| Link stubs for the eight libraries | Generated from the ABI data by `libc-abi-tools` | ≈0.9 MiB, together with the next row |
| `crt1.o`, `crti.o`, `crtn.o`, `libc_nonshared.a` (and `libpthread_nonshared.a` before 2.28) | Built from that release's glibc source | (see above) |
| Installed headers | That release's glibc, plus Linux UAPI headers | ≈1.6 MiB |
| Compiler runtime (`libgcc_s`) and GCC `crtbegin.o`/`crtend.o` | A link-only `libgcc_s` stub with GCC 4.8.5's interface, generated by `libc-abi-tools` for every release; `crtbegin.o`/`crtend.o` from the host GCC | 5 KiB table, compiled into `libc-abi-tools` |

Measured on 2026-10-11 across 25 locally built releases: 30,480 files and 164 MiB
uncompressed, but only 7,576 distinct files (60 MiB). Stored once each, they compress
to 2.6 MiB, because consecutive releases share almost every header and many objects.
**One data crate can therefore hold every release**; there is no need for 28 crates.

## The three modes

### Mode 2: `source` (the default)

Like Zig: ship glibc **source**, not binaries, and compile the startup and
nonshared objects on the user's machine the first time a release is used. Unlike
Zig, compile them with the **host's GCC**: Clang cannot compile these glibc sources
faithfully ([why](#why-source-mode-compiles-with-gcc-not-clang)).

- **Shipped:**
  - each release's installed headers;
  - the original glibc source files for `crt1.o`, `crti.o`, `crtn.o` and every
    `libc_nonshared.a` member (the list changes by release; for example the `stat`
    wrappers leave in 2.33 and `libpthread_nonshared.a` merges in 2.28);
  - the generated configuration headers those files need;
  - the exact compile commands, captured from our pinned container builds.
- **Generated locally:** the link stubs, from the ABI data, as today.
- **Also shipped:** the builder compiler's recorded defaults (its predefined macros).
  Recorded commands leave defaults such as position-independent code implicit, and
  the local compile makes them explicit; it also turns off the host compiler's own
  distribution defaults (stack protector, CET, `_FORTIFY_SOURCE`, stack-clash
  protection).
- **Why it is the default:** no container engine, no binaries from us, and no
  network once the crates are fetched. Shipping source satisfies glibc's
  source obligation directly.
- **Needs:** the host's GCC, which Rust on Linux already uses to link, and GNU binutils.
- **Qualification:**
  - for every release, compare the locally compiled objects with the container-built
    ones: symbols, visibility, sections and references (`glibc-provider-replay`);
  - then run the full application, exhaustive and Cargo suites against the result,
    as for container-built providers.

### Why `source` mode compiles with GCC, not Clang

Decided 2026-10-11, from the replay qualification in
[glibc-provider's REPLAY.md](https://github.com/rustcommons/glibc-provider/blob/main/docs/REPLAY.md).

The design first planned to compile with Clang, as Zig does. Rebuilding every
release's startup and nonshared objects from the recorded sources, and comparing each
object with the container build, gave:

| Compiler | Objects (28 releases) | Byte-identical | Equivalent | Reviewed difference | Wrong | Failed to build |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| GCC 13.3 (host) | 491 | 374 | 112 | 5 | 0 | 0 |
| Clang 18.1.3 | 507 | 136 | 104 | 0 | 49 | 218 |

**What goes wrong with Clang:**

1. **Late attributes are ignored.**
   - glibc's internal headers give some functions an inline body. For example,
     `include/sys/stat.h` defines `extern __inline__ int __stat (...)`, and
     similarly `__mknod` and others.
   - The source file then adds attributes to the same function: `stat.c` marks
     `__stat` `attribute_hidden`, and makes `stat` a weak hidden alias with
     `weak_hidden_alias (__stat, stat)`.
   - GCC applies attributes declared after a definition; Clang ignores them,
     warning only "attribute declaration must precede definition".
   - **Result:** `stat`, `fstat`, `lstat`, `mknod` and their `__` forms come out
     global and visible instead of hidden. The weak `stat` becomes a strong
     definition.
   - **Consequences:** a program or shared library linked with them would export
     these symbols, and a program defining its own `stat` could fail with a
     duplicate definition.
   - **Scope:** the same pattern appears in other internal headers
     (`include/stdlib.h`, `libc_hidden_proto` declarations). It affects 2–14
     objects in every release from 2.17 to 2.42, including `crt1.o`'s parts in
     recent releases.
2. **Linker warnings are emitted wrongly.** glibc's `link_warning` puts a warning
   message in a section named `.gnu.warning.SYMBOL` and appends `"\n\t#"` to the
   name, which comments out the flags GCC writes after it. Clang uses the name
   literally, producing an allocated section with a malformed name. The text would
   then be loaded into programs, and the intended link-time warning lost.
3. **Smaller differences.**
   - Clang places the `_IO_stdin_used` constant in `.rodata` instead of the mergeable
     `.rodata.cst4`.
   - Its code reaches some hidden symbols through the GOT.

   These alone would be acceptable; points 1 and 2 are not.

Making Clang "work" by turning the warning off would silently produce objects with
the wrong symbol visibility, so the replay treats it as an error. Only 2.43 and 2.44
compile fully with Clang, and even there `_IO_stdin_used` differs.

**Why GCC is the right choice:**

- **glibc supports only GCC.** These sources rely on GCC's attribute and
  section semantics.
- **Every user already has GCC.** Rust on Linux links through the system C compiler,
  and providers already take `crtbegin.o`/`crtend.o` from the host GCC.
- **The qualification passes.** With the builder's recorded defaults made explicit,
  the host GCC reproduces every release: 2.37–2.44 byte for byte, and older releases
  equivalent, differing only in instruction selection and relocation encodings.
  - The five reviewed differences are 2.21–2.25's `warning-nop.oS`. Its source
    defines a link-warning alias only for GCC older than 5, and nothing built with a
    modern compiler can reference it.

**GCC versions qualified (2026-10-12):** 11, 12, 13, 14, 15 and 16, both
upstream releases and the distribution builds of Rocky Linux 9, Ubuntu 24.04, Debian 13
and Fedora 43. All reproduce every release, with nothing differing and nothing failing to build
([results](https://github.com/rustcommons/glibc-provider/blob/main/docs/REPLAY.md#gcc-versions-ci-2026-10-12)).
glibc-provider's Replay workflow repeats this on every push and weekly. A compiler
version whose result differs is reported, and `source` mode is not offered with it.

### Mode 1: `prebuilt`

Use exactly the files our CI built and qualified.

- **Shipped:** the startup objects and nonshared archives from the CI container
  builds, byte for byte, with their SHA-256 and the CI run that qualified them. The
  headers are shared with mode 2. The stubs are generated locally as in every mode
  (deterministic), or optionally shipped too.
- **Why:** it is exactly what passed the hosted matrix; it is also the fallback if a
  mode 2 compile fails on an unusual host.
- **Licensing:** this mode redistributes glibc object code, so the LGPL-2.1
  corresponding source must be available to its recipients. That source is the
  pinned GNU archive plus our build scripts and configuration; the archives total
  roughly 400 MB, too large for crates.io. Options to decide:
  - host the archives ourselves next to the binaries (an exception to crates.io-only);
  - ship a written offer of the source, valid for three years (LGPL-2.1 section 6(c));
  - split the source into source-only crates.

  Decide this with legal review before publishing mode 1. See
  [DISTRIBUTION-DIFFERENCES.md](DISTRIBUTION-DIFFERENCES.md#licensing-if-distribution-inputs-are-ever-packaged).

### Mode 3: `container`

Run the same pinned container build that CI runs, on the user's machine.

- **Needs:** podman or docker, network access to the pinned images and package
  archives (CentOS vault, archive.debian.org, snapshot.debian.org), and several
  minutes per release on first use.
- **Why:** the reference for the other two modes, for anyone who wants to build
  everything themselves, and the only mode that also produces the real runtime
  libraries used for runtime testing.
- **Limitation:** it depends on vendor images and archives staying available.
  Replacing them with toolchains built from source is a long-term
  [roadmap](ROADMAP.md#long-term-source-built-builder-toolchains) item.

## Packaging

The current crates, glibc-abilists and the five workspace crates, stay as they are.
New data crates keep licenses separate, as glibc-abilists already does for the ABI lists:

| Crate (names to be decided) | Contents | License |
| --- | --- | --- |
| `glibc-provider-sources` | Deduplicated headers, startup/nonshared sources, generated configuration headers, compile commands, per-release manifests | LGPL-2.1-or-later (glibc), GPL-2.0 WITH Linux-syscall-note (UAPI headers) |
| `glibc-provider-binaries` | Deduplicated CI-built startup objects and nonshared archives, per-release manifests with hashes and CI run | LGPL-2.1-or-later, plus the mode 1 source arrangement |

`libc-abi-tools` gains a `provider` module, following the existing
`bundled-glibc-data` pattern:
- **Feature `provider-sources`** (default) depends on `glibc-provider-sources`.
- **Feature `provider-binaries`** (optional) depends on `glibc-provider-binaries`.
- **Mode 3** needs neither crate.

Because the data arrives as ordinary crate dependencies, `cargo vendor` and offline
builds work unchanged. Each manifest records, per file: path, SHA-256, size, origin
(source or the CI run that produced it), and license.

## Commands

The logic lives in `libc-abi-tools`; cargo-libc depends on it and exposes it. Both
CLIs offer the same operations.

### Using a provider (cargo-libc)

```sh
# Default: no provider flags. A cached provider is used if present; otherwise one
# is prepared in the default mode (source) and cached.
cargo libc build --target x86_64-unknown-linux-gnu.2.28 -- --release

# Choose the mode explicitly (also CARGO_LIBC_PROVIDER_MODE, or config).
cargo libc build --target x86_64-unknown-linux-gnu.2.28 --provider-mode prebuilt -- --release

# Existing explicit forms keep working.
cargo libc build --provider /path/provider.txt --target x86_64-unknown-linux-gnu.2.28
cargo libc build --sysroot DIR --gcc-runtime DIR --glibc 2.28
```

`check`, `test`, `run`, `inspect` and `doctor` accept the same selection.
`--provider FILE` and `--sysroot` take precedence over automatic preparation, and
a mismatched release is still refused.

### Managing providers

```sh
cargo libc provider prepare --glibc 2.28 [--mode source|prebuilt|container]
cargo libc provider list                    # cached providers: release, mode, hashes, origin
cargo libc provider path --glibc 2.28       # descriptor path, for scripts and plain Cargo
cargo libc provider verify --glibc 2.28     # recheck hashes and rerun the stub/ABI audit
cargo libc provider export --glibc 2.28 --to DIR   # copy to an offline machine
cargo libc provider import DIR
cargo libc provider remove --glibc 2.28 [--mode M]
```

The same operations exist as `libc-abi provider ...` for users who do not use
cargo-libc. `prepare` without `--glibc` accepts `--all`.

### Cache

```text
$CARGO_HOME/libc-providers/x86_64-unknown-linux-gnu/glibc-2.28/<mode>-<content-hash>/
    provider.txt  sysroot/  stubs/  compiler-runtime/  manifest.json
```

The cache location can be overridden with `CARGO_LIBC_PROVIDER_DIR`. The content
hash covers every input (manifest hashes, tool versions, compile commands), so
changed inputs never reuse a stale provider. Each entry's `manifest.json` records
its mode and origin.

### Descriptor

The v1 descriptor stays six fields. A provider prepared by any mode records its mode
and content hash in `manifest.json` next to it. If tools need the mode, a v2
descriptor adds an explicit `mode` field, documented before use, and v1 stays
accepted.

## Qualification of all three modes

Hosted CI already qualifies the container builds for every release (84 jobs). For
delivery it additionally:

1. publishes the data crates only from a commit whose container builds passed;
2. for each release, prepares the provider in each mode from the published (or
   about-to-be-published) crates and compares the results:
   - stubs and headers byte-identical in all modes;
   - mode 1 objects byte-identical to the container build;
   - mode 2 objects equivalent in symbols, versions, sections and relocations;
3. runs the application, Cargo, scan, runner and rejection suites against each
   mode's provider;
4. records per release and mode, in [PROVIDERS.md](PROVIDERS.md), which modes
   passed and on which run.

A mode that fails for a release is reported for that release and not offered there,
rather than silently falling back to another mode.

## Decisions (2026-10-11)

1. **Data crates:**
   - `glibc-provider-sources` and `glibc-provider-binaries`, both free on crates.io.
   - Versioned independently of the workspace, as glibc-abilists is: a minor version
     when a glibc release is added, a patch for corrections.
   - `libc-abi-tools` depends on them with `^` requirements.
2. **Source for `prebuilt`:**
   - `glibc-provider-binaries` depends on `glibc-provider-sources`, so the binaries
     never travel without their source.
   - For every shipped object, the sources crate carries every source file it was
     compiled from (taken from the compiler's dependency output), the generated
     configuration headers, our build scripts and configure options, and a pinned
     reference with hash to the full GNU archive.
   - Legal review of this arrangement comes before `prebuilt` is published. `source`
     and `container` ship first.
3. **Compiler runtime:**
   - A generated link-only `libgcc_s` stub with CentOS 7's GCC 4.8.5 version set,
     used for every release, so no GCC binary is shipped. **Implemented
     2026-10-12** ([details](#the-libgcc_s-stub)).
   - `crtbegin.o`/`crtend.o` keep coming from the host GCC; compiler-rt stays a later
     option.

## The `libgcc_s` stub

Rust programs on Linux link `libgcc_s.so.1` for unwinding. Linked against a newer
GCC's library, a program can record symbol versions an old system's runtime lacks
(GCC 7 added `GCC_7.0.0`, GCC 12 `GCC_12.0.0`, and so on), and the old loader then
refuses it. Every provider therefore links against a stub with the interface of GCC
4.8.5's `libgcc_s.so.1`, the runtime of CentOS 7, the oldest supported target.

- **The record:** `src/libgcc_s-gcc-4.8.5.tsv` in `libc-abi-tools` lists the 138
  definitions of that library (name, version, default or compatibility version, type,
  size, and alignment of its one object, `__cpu_model`), and nothing else of it.
  `scripts/record-libgcc-s.sh` measures it from CentOS 7's package
  `libgcc-4.8.5-44.el7.x86_64` (SHA-256 `8f148d8b…`) in the pinned builder image; CI
  repeats that measurement and requires the same table.
- **The stub:** `libc-abi libgcc stub --output DIR` writes its assembly and version
  script, and `as` and `ld -shared` build it, as for the glibc stubs. It exports exactly
  those 138 definitions, with GCC's version chain (`GCC_3.0` … `GCC_4.8.0`, each
  inheriting the previous one), and contains no code: every function body is a trap.
- **At run time** a program uses the target system's real `libgcc_s.so.1`. Any GCC
  from 4.8.5 on provides every definition the stub has, so the program loads there.
- **Qualification, every release** (glibc provider integration workflow):
  - the stub's exports and version chain equal the record; for 2.17–2.25 the
    builder's own library is GCC 4.8.5's, and must equal the record too;
  - the real library each test runs with provides every recorded definition;
  - every Rust program built (directly and through cargo-libc) imports from
    `libgcc_s` only recorded definitions, and is loaded with the real library, never
    the stub;
  - a link needing a newer interface (the oldest the host's GCC has beyond 4.8.5)
    fails against the stub, while the same object links against the host's library.

## Remaining questions

- **Headers:** mode 2 needs no network but adds about 1.6 MiB of headers to every
  install. A headers-optional build is possible for pure-Rust users, whose builds
  only need `features.h` for validation.
