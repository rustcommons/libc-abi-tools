# Comparing prebuilt and source built glibc inputs

This experiment builds the same small C program for x86_64 Linux using two
glibc 2.17 environments. It makes the input sourcing decision in the project
roadmap concrete. It uses real libc libraries; generated ABI stubs and
cargo-libc integration are separate future stages.

## The program and the control

`hello.c` calls `puts` to print one line. Even this program needs startup code
to reach `main`, headers to compile the call, and libc to implement it.

The native control uses Ubuntu's normal compiler configuration. The two target
builds compile on that same newer host, but explicitly select old glibc headers,
startup objects, linker scripts, and libraries. Compiler-provided `crtbegin.o`
and `crtend.o` still come from the newer compiler and are recorded in link maps.
This example does not require linking libgcc or libstdc++; other programs can.

## Where the files come from

| Input | Prebuilt route | Source route |
| --- | --- | --- |
| glibc headers | CentOS glibc development packages | Installed by the upstream glibc build |
| `crt1.o`, `crti.o`, `crtn.o` | CentOS glibc development packages | Compiled from upstream glibc source |
| `libc_nonshared.a` and libc linker script | CentOS glibc development packages | Compiled/generated by the glibc build |
| libc and dynamic loader | CentOS runtime packages | Compiled from upstream glibc source |
| Linux UAPI headers | CentOS kernel-headers package | Same separate kernel-headers package |
| Compiler startup objects for the application | Ubuntu GCC | Ubuntu GCC |
| Tools used to build glibc | Not needed to consume the prebuilt files | CentOS GCC 4.8.5, binutils, make, and gawk |

The source route rebuilds glibc, not the entire toolchain. It deliberately uses
a prebuilt older compiler and kernel headers. A fully source-built SDK would
also need build recipes for those components and their dependencies.

The prebuilt tree is an intentionally broad copy of development/runtime
directories, not a minimal distributable SDK. CentOS's patched glibc and the
upstream glibc 2.17 release are different builds; sharing the version number
does not make their files identical.

## Reproduce on Linux

Requirements: x86_64 Linux, rootless Podman, GCC, GNU binutils, curl, sha256sum,
network access, and enough storage for the container and glibc build. Use a
Linux filesystem for build output; on Windows, run through WSL.

From the repository root:

```sh
bash examples/glibc-two-paths/run.sh /tmp/libc-abi-two-paths-new
```

The work directory must not exist. The script downloads the source, pulls the
pinned builder, installs packages inside a disposable container, assembles the
two input trees, builds glibc, and then links and runs the examples on the host.
It does not install old glibc into the host. It retains inputs and logs in the
work directory, and Podman retains the downloaded image.

Pins used for the experiment:

- Builder: `docker.io/library/centos@sha256:dead07b4d8ed7e29e98de0f4504d87e8880d4347859d839686a31da35a3b532f`.
- Package source: [CentOS 7.9.2009 archive](https://vault.centos.org/7.9.2009/os/x86_64/).
  Package signature checking is enabled. Exact installed versions are recorded
  in `logs/packages.txt`; package payload checksums are not separately locked.
- Source: [GNU glibc 2.17 archive](https://ftp.gnu.org/gnu/glibc/glibc-2.17.tar.xz).
  SHA-256: `6914e337401e0e0ade23694e1b2c52a5f09e4eda3270c67e7c3ba93a89b5b23e`.
  This checksum records the downloaded bytes; an upstream signature has not
  been independently verified for this experiment.
- Configuration: `--prefix=/usr --disable-werror --enable-kernel=2.6.32`.
  This is a build setting, not evidence of testing on that kernel.

The first source-build attempt omitted `-ffreestanding` and repeatedly rebuilt
the syscall header dependencies. GCC 4.8 implicitly included `stdc-predef.h`,
which this old glibc build also installed. Freestanding compilation avoids that
implicit include. The recipe patches only the two syscall-header preprocessing
commands to add that flag, and records the diff in `logs/source-adjustment.patch`.
Applying it globally interferes with configure's builtin-function checks;
putting it only in `CFLAGS` misses the affected commands.

Keep the source archive, its license files, package provenance, and logs with
the local experiment. This recipe does not establish redistribution compliance
or byte-for-byte reproducibility.

## Read the evidence

Observed on 2026-10-09 using Ubuntu 24.04 WSL, host GCC 13.3.0, and the isolated
CentOS GCC 4.8.5 builder:

| Build | glibc requirements for `puts` / `__libc_start_main` | Run with glibc 2.17 |
| --- | --- | --- |
| Normal Ubuntu control | `GLIBC_2.2.5` / `GLIBC_2.34` | Rejected: `GLIBC_2.34` not found |
| Prebuilt CentOS inputs | `GLIBC_2.2.5` / `GLIBC_2.2.5` | Printed the expected line |
| Built upstream inputs | `GLIBC_2.2.5` / `GLIBC_2.2.5` | Printed the expected line |

The prebuilt glibc development package was `glibc-devel-2.17-317.el7.x86_64`;
kernel headers were `kernel-headers-3.10.0-1160.el7.x86_64`.
Both target binaries list only `libc.so.6` as a needed shared library.
The repository's glibc 2.17 symbol queries independently report `GLIBC_2.2.5`
for both functions, consistent with the executable inspection.

Local output is in `/tmp/libc-abi-two-paths-clean` in Ubuntu WSL. A copy of the
logs is retained under the ignored repository directory
`validation-output/glibc-two-paths/logs`. The first unsuccessful source attempt
remains under `/tmp/libc-abi-two-paths`.

`logs/*-versions.txt` records ELF symbol version requirements.
`logs/*-symbols.txt` identifies the symbols attached to those versions.
`logs/*-link.map` records linker inputs, including startup objects and nonshared
archive members actually selected. `logs/*-dynamic.txt` records runtime library
dependencies; `logs/*-program-headers.txt` records the interpreter path.

The target executable is run using each tree's actual glibc 2.17 loader and
library search path. Simply running it normally on Ubuntu would exercise
Ubuntu's installed runtime and would not prove the old-runtime case.

The native control is also run with the prebuilt old runtime and must fail with
a missing glibc symbol version on a suitably newer host.

These checks cover one non-PIE C executable on a newer WSL kernel. They do not
qualify an old Linux distribution, threads, TLS, C++, unwinding, Rust builds,
native dependencies, or a general compiler runtime policy.

## What the experiment means for the project

The prebuilt route requires identifying a coherent package set, extracting it,
checking its provenance and integrity, and verifying compatibility. The source
route requires those controls plus a builder, configuration, compatibility
adjustments, build logs, and maintenance of the build recipe.

Both routes still need real startup and nonshared code. In the prebuilt link
map, `crt1.o` references `__libc_csu_init`, and the linker selects
`libc_nonshared.a(elf-init.oS)` to supply it. This is code in the executable,
not a symbol that a future link-only DSO can implement.

## Minimal generated library experiment

The follow-up experiment replaces real libc at link time with a generated
two-function DSO. Run from the repository root on Linux, with Cargo on PATH:

```sh
bash examples/glibc-two-paths/stub-and-check.sh /tmp/libc-abi-two-paths-clean
```

It requires the existing `prebuilt` and `source` input trees, Rust/Cargo,
GNU binutils, GCC, and Python 3. The generator refuses an existing
`generated-stub` directory. Use newly assembled trees for a fresh complete run;
an interrupted generation can leave a partial directory for inspection.

`examples/minimal_glibc_stub.rs` reads the pinned 2.17 snapshot and generates
assembly and a [GNU ld version script](https://sourceware.org/binutils/docs/ld/VERSION.html).
It exports only `puts@@GLIBC_2.2.5` and `__libc_start_main@@GLIBC_2.2.5`, uses
SONAME `libc.so.6`, and supplies trap instructions rather than implementations.
It is a standalone Cargo example; the main metadata CLI is unchanged.

Both reference ELF libraries export `puts` with weak binding and startup with
global binding, using default visibility and the listed default versions.
The ABI lists do not supply those binding/default properties. The generator
reads them from real ELF evidence using the native Rust collector. It supports
only these two ordinary default-visible functions, and the verifier checks them
against both real libraries, recording hashes and selected exports in
`logs/stub-real-elf-evidence.tsv`. Alias relationships are outside this scope.

The executable link receives the stub, real CRT objects, and an explicit real
`libc_nonshared.a`. No real shared libc or loader is supplied to the linker.
At runtime, the old real loader resolves the `libc.so.6` dependency using the
real input tree. No stub path is embedded in either executable.

Observed on 2026-10-09:

- Both input routes linked and printed the expected line with real glibc 2.17.
- ELF checks verified default versions, function kind, binding, visibility,
  SONAME, executable requirements, and real runtime libc selection.
- Link maps retained `libc_nonshared.a(elf-init.oS)` and the generated DSO.
- Repeated assembly/linking produced byte-identical stub DSOs with this toolchain.
- `too-new.c` failed to link in both routes with an undefined `memfd_create`.
  Pinned snapshots show that export absent in 2.17 and present at `GLIBC_2.27`
  in the 2.27 snapshot.

The negative test covers this specific absent symbol; a two-function stub also
rejects many valid older APIs. This is not full glibc generation or a supported
link environment. Multi-version aliases, data/TLS exports, other libraries,
Rust integration, and old-distribution qualification remain future work.

`selected-elf.tsv` records the generator's selected reference evidence.
The [ELF metadata collector](../../docs/ELF-METADATA.md) additionally checks all
eight libraries in both input trees against readelf and the pinned ABI snapshot.
The next step is to expand the generator using that evidence, with explicit
handling of multi-version functions, IFUNC, data/TLS, and unresolved alias rules.

The [expanded generator experiment](../../docs/STUB-GENERATION.md) now covers
those selected properties using the same real inputs and an original ELF fixture.
Run `expanded-and-check.sh` with the existing experiment directory to reproduce it.

The [full-library follow-up](../../docs/FULL-LIBRARIES.md) now generates all
public numeric GLIBC 2.17 definitions in the eight selected libraries and builds
a Rust allocation/thread/TLS-destruction/unwind program with both old runtimes.
Run `full-and-check.sh` for that experiment. It links against a generated
`libgcc_s` stub with GCC 4.8.5's interface and runs with the builder's real old
compiler runtime, never the host unwinder.

`full-and-check.sh` is now a convenience wrapper for `prepare-and-check.sh` and
`application-and-check.sh`. Hosted CI runs preparation once per release, then
transfers checked inputs to Rust 1.99/Clang 21 and 24 application jobs; Cargo
integration remains in `provider-and-check.sh`. See [CI and release artifacts](../../docs/CI-AND-RELEASE-ARTIFACTS.md).
